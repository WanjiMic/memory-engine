# 把记忆接进对话模型

引擎只负责「存和找」，不负责「说」。这份文档给的是接线方式：什么时候查、查到的怎么拼进上下文、聊完怎么写回去。

## 一、上下文装配顺序

每轮请求拼给模型的内容，固定这个顺序（越靠前越不容易被模型忽略）：

1. **身份与规矩**：你是谁、跟用户什么关系、硬性约束。短句，不用长文。
2. **今日账本**：最近一天或两天的流水。模型需要知道「刚刚发生了什么」。
3. **检索命中**：本轮相关记忆，带来源和日期。没命中就不放，不要用「暂无相关记忆」占位。
4. **冷记忆**（可选）：如果命中了冷记忆，单独一节，明确标「这是很久以前的事，可能已不准确」。
5. **原话与出处**：命中的正本行号，拼在命中项后面，让模型引用时能说清来源。
6. **本轮用户消息**。

不要让模型自己决定查不查——查询由外层代码在调用模型前完成。模型的任务是「用了哪些、怎么用」，不是「去不去找」。

## 二、系统提示骨架

```text
你是 <助手名>。你和用户的关系是 <关系>。

你的记忆来自本地文件，不是训练数据。涉及过去的事实，以检索结果为准；
检索结果没有的，就说不知道，不要编。

回答时如果引用了记忆，带上它的日期；用户问「你怎么知道的」，
给出出处（文件名和行号）。

写入记忆的规矩：
- 只写用户确认过的事实和原话
- 不写你的推测，除非明确标成推测
- 每次写完，说明写了什么、写在哪
```

原则：提示只写「行为约束」，不写「内容」。内容都在检索结果里。

## 三、检索结果模板

```text
## 相关记忆（共 {n} 条）

### {heading}（{date}，{source}{line_ref}）
{text}

...
```

如果某条来自冷记忆，段落前加：

```text
〔冷记忆〕这条记录的权重已低于阈值，可能过时或不准确，引用前先跟用户核对。
```

如果一条都没有，整个小节省略。空小节会让模型以为「查过了、确实没有」，而实际上可能是查询词写错了。

## 四、写回

一段对话结束后，写入分三步，顺序不能反：

1. **账本先行**：把今天发生的事写进账本（`## YYYY-MM-DD` 下面）。账本是事实层，用原话和细节，不写概括。
2. **抽卡**：从账本里挑「以后会被问到的」抽成卡。一张卡一件事，带日期、类型、权重（可省略，导入时按类型算）。
3. **更新索引**：重跑导入（或等下次查询自动重建）。

卡片格式（`cards` 指向的 JSONL，一行一张）：

```json
{"id": "e20261117-1", "date": "2026-11-17", "k": "事件", "w": 60, "text": "……", "refs": ["账本.md#L12"]}
```

- `id`：`e` + 日期 + `-` + 当日序号。这个格式被检索代码用来识别「这是一张卡」。
- `k`：类型，`事件` / `情绪` / `决定` / `规则`。类型决定衰减速率。
- `w`：可选。不写就按类型算。
- `refs`：正本里的出处，`path#L行号`。越准，以后原话越不会错。

## 五、三个反模式

1. **把整个账本塞进上下文**。会挤掉检索结果，模型也更偏向最近的内容。账本只放最近一两天。
2. **让模型自己决定记什么**。模型倾向于记「对话本身」而不是「事实」。抽卡规则由外层定：什么类型进卡、一天抽几张。
3. **把检索结果当结论**。检索只给「可能相关的材料」，给模型的话要注明「以下是材料，不是答案」。材料里可以有矛盾，让模型指出矛盾，而不是选一个。

## 六、最小闭环

```text
用户消息 → 拆词 → 检索 → 拼上下文 → 模型回答
                                    ↓
                              账本追加 → 抽卡 → 重建索引
```

这个闭环里没有「记忆管理页面」，也没有「用户手动编辑记忆」的入口——正本就是编辑器，改完重跑导入即可。少一个界面，少一处不同步。
